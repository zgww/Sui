用"树"表达状态流转？先分清三种"树"

层次状态机 HSM、行为树 BT、纯状态树是三种不同范式；结论先行：流转本身是图不是树，但"结构"用树、"任务"用行为树确有价值。
前提：状态"流转"天然是图，不是树。树要求单父、无环、根→叶单向；而真实流转里大量存在 回环：就位优化 →超时→ 移动中（重试） 回退：充电完成 → 空闲（回到更早状态） 多入口：空闲可被复位/急停解除/上电等多个事件进入 纯树表达这些只能靠"复制状态节点"hack，导致同一状态出现多份、当前态无法追踪。
① 层次状态机 HSM
状态嵌套状态；事件从叶子沿父链冒泡，父级可放公共迁移。树表达的是"包含结构"。
适合：多个状态共享急停/暂停/故障迁移、模式嵌套、进入父态自动入初始子态、history 记忆。
成本：嵌套盒子编辑器、事件冒泡优先级、逐层 enter/exit、history 语义，内核复杂度上升一档。
② 行为树 BT
节点不是状态而是被 tick 的行为，返回 成功/运行中/失败；树表达的是"任务分解与决策"。
内置节点，不必画状态和回线
适合：巡检/对接等有步骤、重试、超时、失败兜底、反应式的任务（Nav2/ROS 主流做法）。
成本：另一套范式与编辑器；不擅长长期模态（充电中/手动模式），每 tick 重评估。
③ 纯状态树（状态做节点、迁移做父子边）
把"流转"本身画成树——不推荐，表达力倒退。
问题：树只能表达"分解/包含"，表达不了"可能回 A、可能去 B、还可能循环"的流转。

对照：与现有 FsmSpec 的关系

范式 最擅长 在本项目的位置 改动量
HSM 长期模式、公共迁移复用、嵌套封装 FsmSpec 的"子状态机激活 + LIFO 栈"已是 HSM 的受限子集；补复合状态/事件冒泡/父级公共迁移/history 即可平滑升级，不推翻 中（演进而非重写）
行为树 步骤序列、重试/超时/兜底、并行、随时反应（避障/急停） 替代的是"某个状态内部的任务流程"（巡检/对接），经 handler 当动作执行器接入；不替代顶层模式管理 中（新增一层，并存）
纯状态树 仅适合无环、单向、不回头的向导式流程 机器人有大量重试/回退/循环，不适用 —（不建议）

推荐：不是二选一，而是 FSM/HSM 管模式 + BT 管任务

怎么决定要不要做、先做哪个？看你的真实痛点：
· 若痛点是「急停/暂停/故障迁移在每个状态下都要重复连一遍、模式有明显包含关系」→ 走 HSM 演进（在 FsmSpec 上加复合状态 + 事件冒泡 + 公共迁移）。
· 若痛点是「巡检/对接里的顺序、重试、超时、失败兜底要画一堆状态和回线，图越来越密」→ 给该状态内部引入 行为树（重试/超时/顺序是内置节点，节点数和回线大幅减少，且天然反应式）。
· 若只是觉得「树看起来比图整齐」→ 不建议为整齐换范式，会丢掉回环/回退/多入口。
务实路径：FsmSpec 先保持现状跑通 RobotCtrl；等真出现上面某类痛点，再按 HSM（结构复用）或 BT（任务流程）按需演进，二者都能挂在现有 handler 接缝上，不必推倒重来。
