# 测点档案 JSON 性能评估

## 环境与方法

2026-09-17，在部署机 `192.168.6.88` 的独立临时容器执行；ARM64、Python 3.11.16、1 CPU 配额、512 MiB 内存限制、禁用网络。无生产 data 挂载，不导入 FMS 程序，不读写线上档案/数据库。

脚本：`../../backend/scripts/benchmark_point_archive.py`；原始数据：[point-archive-20260917.json](point-archive-20260917.json)。

每条合成记录约 640 字节，包含中文名称、设备/层级、编码、检测配置、来源、时间与扩展字段。每设备 100 点。50 条分页；名称条件命中全部记录，再以检测类型筛选约 20%。最后一条 ID 查找模拟数组扫描较差情况。

耗时使用 perf_counter_ns，常规查询 50 次，解析/建索引 20 次，写入 5 次；字典查询每组 10,000 次摊销，设备分页每组 1,000 次摊销。下表为中位数；p95 在原始 JSON 中。读文件是**热文件缓存**，没有清理操作系统缓存，不代表冷盘启动时间。写入包含文件与父目录 fsync、原子替换，不包含备份/权限/引用校验。

## 结果

| 指标 | 1,000 点 | 10,000 点（用户规模上界） | 50,000 点（扩展观察） |
|---|---:|---:|---:|
| JSON 大小 MiB | 0.614 | 6.167 | 30.963 |
| Python 对象与三个索引常驻 MiB | 2.066 | 20.566 | 104.648 |
| 加载与建索引期间 Python 分配峰值 MiB | 3.110 | 31.155 | 156.162 |
| 读文件 + 解析 ms | 9.647 | 117.605 | 781.118 |
| 单独建三个索引 ms | 0.405 | 4.814 | 37.764 |
| 每请求读/解析/扫描取最后 ID ms | 9.717 | 117.357 | 796.340 |
| 已加载数组扫描最后 ID ms | 0.067 | 1.037 | 12.596 |
| 内存 ID 索引查询 ms | <0.001 | <0.001 | <0.001 |
| 设备索引取 50 条 ms | <0.001 | <0.001 | <0.001 |
| 内存名称 + 类型全表过滤 ms | 0.168 | 1.720 | 12.673 |
| 序列化 50 条 JSON ms | 0.567 | 0.554 | 0.529 |
| 整文件原子发布 ms | 49.425 | 452.501 | 2246.087 |

## 解释与局限

- 1 万点下，逐请求解析是约百毫秒的额外成本；后端常驻缓存与索引足以消除这部分重复开销。
- 低频整文件发布约 0.45 秒，适合配置维护，不适合将检测结果不断追加改写进去。
- 内存数据约为 JSON 文件体积的 3 倍以上，不能把磁盘文件大小当运行内存需求。数值来自 tracemalloc，不是容器 RSS；不包含完整 FastAPI、额外索引、Pydantic 对象或同时保留新旧快照的成本。
- 该服务器不是所有机器人的等效硬件。容器 CPU 配额也不等同于低端设备，不能直接承诺现场延迟。
- 本实验没有 HTTP、鉴权、并发、SQLite 绑定关联、父级名称拼接、完整 Schema 校验或与数据库的对照压测；不证明 JSON 比 SQLite 快，也不证明 API 已达到 100 ms。
- 部署实现后用真实数据在目标硬件复测 10 并发、50 条分页、名称/绑定联合筛选、初次加载与版本重载；若档案需热更新，测双快照峰值。

结论：支持在 **1 万以内、低频修改、单进程写入** 的前提下采用 JSON 档案 + 内存索引。动态关系和运行记录保留 SQLite。

## 复现

在任意 Python 3.11 环境：

```bash
python backend/scripts/benchmark_point_archive.py --sizes 1000 10000 50000
```

容器复现时挂载该脚本为 `/benchmark.py`，使用 `python:3.11-slim`、`--cpus 1 --memory 512m --network none`，执行 `python /benchmark.py`。Python 镜像补丁版本变化和服务器负载会影响结果；本记录保留了实际版本与原始分位数。
