两套状态机方案对比 · 过程式手写（sm.py） vs 声明式解释（FsmSpec）

评分为针对本项目（挂轨机器人 FMS、已投入 FsmEditor、数据驱动架构）的主观工程判断，5 分制，非绝对优劣。
方案 A · 过程式手写（sm.py）
状态/迁移/条件/动作全写在 behXxx() 的 if st==… if sig==… 里；内核 + 业务耦合在一个文件；信号入队、每 tick 轮询。逻辑即代码，改行为=改 Python 发版。
方案 B · 声明式数据驱动（FsmSpec）
状态/迁移/激活是数据（.fsm.json，可视化编辑），通用解释器读数据执行，业务动作经 handler 回调外抛，编译期校验图。行为即数据，很多改动=改图不发版。

多维评分（灰=A，蓝=B）

关键差异

维度 方案 A 过程式 方案 B 声明式
表达上限 图灵完备，任意条件/循环/动态决策；复杂后摊成巨大嵌套分支 受图元语义约束，DSL 天花板即边界；非状态机逻辑（运动规划/视觉判定）会别扭
正确性 靠人自觉；级联迁移、信号竞争、定时器泄漏已实际发生，错误多在特定时序暴露 编译期拦截悬空线/无归属/跨机/重复迁移；确定性内核集中测一次（已 17 例）
改行为 改代码、加分支、重新发版；多机靠复制粘贴，行为漂移 常规改动=画图/配置，可不发版、可热更；多机共用内核、不同 spec
可视化 编辑器与运行时两张皮，图会过时沦为摆设 图即程序，可做激活态高亮/单步/迁移回放，兑现 FsmEditor 投入
成本与门槛 零新概念，会 Python 就能写、能打断点；短期最快 前期要建解释器+编辑器+handler 协议；要理解激活栈/complete/LIFO；内核是单点
主要风险 流程增多后维护成本非线性上升、改一处怕动全身、依赖原作者记忆 handler 里偷塞状态决策会重新两张皮；DSL 滥加图元会膨胀；schema 版本兼容

结论：不是取代，而是分工

用 B（FsmSpec）承载顶层编排
巡检/充电/切楼层/模式切换/异常恢复等可枚举、需可视化与现场调整、要复用热更的行为——约占机器人顶层逻辑 80%。
算法类逻辑留在 DSL 之外
运动规划/避障、视觉判定、信号处理等难画成有限状态的能力写成普通服务，由 handler 调用。状态机管"何时做、何时转"，算法管"怎么做"。
sm.py 的定位：它是有价值的需求草稿/思维工具——已把充电、切楼层、巡检的状态与流程梳理清楚；这些应翻译成 spec（example_charge 即示范），之后 sm.py 可废弃。
B 成功的三个前提：① DSL 保持小而稳，新需求优先用现有图元表达、确需时才审慎加图元；② handler 守纪律——只执行动作，不偷做状态迁移决策；③ 工具闭环——补齐编辑器字段（sm/timeout/on_enter）+ 运行时激活态高亮/单步，否则团队会退回写代码。
